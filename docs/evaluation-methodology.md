# Evaluation methodology

## Tier A — deterministic (no LLM)

* **Conformance**: `fixtures/` golden vectors run in all three runtimes (syntax → plan, codec round
  trip, negative syntax/plans, execution incl. mutations). Generated by the .NET reference
  (`Rql.Conformance regen`), reviewed by hand, never edited to make a runtime pass.
* **Benchmarks**: `dotnet/Rql.Bench` measures per-query median/p90 wall time, allocated bytes, visited
  objects, members read and encoded output bytes on the Large (14k objects) and Huge (145k objects)
  worlds, for compiled vs reflection accessors. Saved to `evaluation/reports/tierA-*.json`.
* **Task self-check**: `rql-eval reference --split all` runs a scripted reference RQL solution for every
  task through the same host/tool surface and grades it with the hidden grader. This cross-checks the
  executor against independent LINQ oracles and proves every task is solvable (must be 100%).

## Tier B — agent in the loop

* **Tasks**: catalog `v1` (`evaluation/runner/Rql.Eval/Tasks/Catalog.cs`), 47 templates (32 dev, 15 holdout) in 8 categories
  (find, read, aggregate, traverse, modify, find-modify, negative, scale), each instantiated per seed
  with parameters drawn from the generated world. Splits: **dev** (seeds 11, 12; 62 instances; used for
  tuning) and **holdout** (separate templates, seeds 21, 22; 27 instances; only for checkpoints).
  Public task text: `evaluation/tasks/tasks-v1-all.jsonl` (no answers).
* **Oracle/grader** (hidden from the model): expected results computed with LINQ over the live sandbox.
  Set answers are graded by exact set equality (precision/recall recorded). Numbers use a tolerance.
  Objects are compared field by field. Mutation tasks: a fresh sandbox + intended change is
  snapshotted (`GraphSnapshot`, every owning scalar path) and compared to the agent's final state.
  Any diff fails, and unintended changes are counted separately. Negative tasks require `NONE` /
  `IMPOSSIBLE` and an unchanged world.
* **Agent loop**: OpenAI-compatible chat completions with tools `rql_query`, `rql_mutate` (mutation tasks
  only), `rql_schema`, `submit_answer`. Fixed per condition: model, endpoint, system prompt variant,
  temperature (0, non-thinking) or reasoning effort, `maxSteps` 12, `maxTokensPerCall` 4096, rows per
  result 50. DeepSeek `reasoning_content` is passed back as the provider requires with tools.
* **Metrics**: provider-reported usage per request (`prompt_tokens`, cache hit/miss, completion,
  reasoning). Cost = usage × the versioned price snapshot (`configs/pricing.json`, with peak/off-peak
  by request UTC time; Chinese public holidays not modelled, which is conservative). Also wall time,
  model turns, tool calls/errors (by code), protocol errors, tool-result characters, and executor time.
  Reports give exact success with a Wilson 95% CI, cost per successful task, successes per $ and per
  wall-minute, median/p95 latency, and paired per-task flips.
* **Comparisons**: one factor at a time, paired by (task, repeat), 3 repeats per task (temperature 0 is
  still not deterministic on this provider; flips in both directions appear). Accept a change only if
  success does not regress beyond noise and an explicit objective improves. Holdout is evaluated only
  at checkpoints (baseline vs current), never used to tune.
* **Cost noise**: provider prompt caching makes cost partly depend on what else ran concurrently (cache hits
  cost ~2% of misses). The cache-hit ratio is reported per run. Cost deltas below ~15% are not
  meaningful by themselves; token counts and tool calls are the more stable efficiency signals.
* **Grader fixes** are applied retroactively to stored answers with `rql-eval regrade` (originals kept
  in `results.orig.jsonl`) and reported as such.
* **Spend**: `evaluation/baselines/spend-ledger.json` accumulates every run (incrementally per task),
  with a global cap (`CapUsd`) and a per-run cap from the config.

## Threats to validity

* Single provider/model family (DeepSeek V4.1-Flash; one spot check with V4-Pro). Results on other
  models may differ.
* The sandbox and tasks were designed by the same author as the language. Holdout templates
  mitigate but do not eliminate this bias.
* Dev was used for iterative tuning and reached 100%; the dev numbers after E3 measure efficiency
  more than capability. Holdout is the honest success estimate.
* Per-task sample sizes are small (n = 186 dev / 81 holdout runs per condition); CIs are reported.

## Running it

```bash
scripts/rql-eval tasks --split all          # public task list (no answers) → evaluation/tasks/
scripts/rql-eval reference --split all      # scripted reference agent; must be 89/89 (no LLM, no cost)
export RQL_EVAL_API_KEY_FILE=/path/to/key   # or RQL_EVAL_API_KEY; never commit keys (.env is gitignored)
scripts/rql-eval probe --config evaluation/configs/v2.json
scripts/rql-eval run --config evaluation/configs/v2.json --split dev --repeats 3 --out evaluation/runs/my-run
scripts/rql-eval run ... --set Prompt=v3 --set SchemaInPrompt=true      # one-factor overrides
scripts/rql-eval report evaluation/runs/A evaluation/runs/B             # paired comparison
dotnet run -c Release --project dotnet/Rql.Bench -- --size large        # Tier A benchmarks
```

Raw traces stay in the gitignored `evaluation/runs/`.
